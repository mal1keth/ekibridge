# The ekicore C ABI contract

This document is the normative description of the C interface declared in
[`include/ekicore.h`](../include/ekicore.h), ABI version 2. Both `libekicore` (C++, OpenSSL) and
`libekicore_rs` (Rust, RustCrypto) implement it, and the conformance harness checks that they
behave identically. Where this document and the header disagree on a declaration, the header wins;
where they disagree on behaviour, this document wins and the implementation is the bug. Where the
two libraries differ in a way the contract leaves open, [Known differences](#known-differences)
says so.

## Purpose and scope

The ABI covers:

- HMAC-SHA256 (compute and constant-time verify),
- HKDF-SHA256 (RFC 5869, extract and expand in one call),
- AEAD: AES-256-GCM and ChaCha20-Poly1305 with detached 16-byte tags and 12-byte nonces,
- ECDSA P-256 / SHA-256 signature verification (`r || s` signatures, SEC1 uncompressed keys),
- a key store with a software backend and a PKCS#11 backend: generate, inspect, sign, HMAC, wrap
  and unwrap (RFC 3394 AES key wrap), destroy,
- key lifecycle states (active, retired, revoked) with rotation and revocation,
- an append-only, hash-chained audit log of key store calls, and its verifier,
- dual control of destroy: two of up to eight approver keys must sign a destroy request,
- a hybrid X25519 + ML-KEM-768 KEM, compiled in only with the `pq` feature / `EKI_WITH_PQ`.

Out of scope: certificates and PKI (see [the PKI note](pki-note.md)), key persistence for the
software backend, streaming (all inputs are complete buffers), and any algorithm not listed above.

The header is generated by cbindgen from the Rust declarations (`abi/` and `core-rs/src/ffi.rs`)
and committed. The C++ library compiles against the committed header, so the compiler enforces that
C++ matches it; CI regenerates the header with a pinned cbindgen and fails on any difference, which
enforces that Rust matches it ([`scripts/check-header.sh`](../scripts/check-header.sh)).

## Ownership and allocation

- The library never retains a caller pointer after a call returns. The strings of
  `eki_ks_config` and `eki_ks_config_v2` and the approver keys are copied during the open call.
- The only object the library allocates for the caller is the opaque `eki_ks` handle. It is
  created by `eki_ks_open` or `eki_ks_open_v2` and released only by `eki_ks_close` (which accepts
  NULL). The caller never frees it any other way.
- Every other output is written into caller-provided memory of the size documented per function.
- Strings returned by `eki_version` and `eki_status_name` have static storage and must not be
  freed.
- The audit log file belongs to the handle that opened it for the life of the handle; the library
  creates it when it is missing and never deletes or truncates it, except to cut off a record it
  failed to write in full (see [Writing](#writing)).

## Pointer and length rules

For each input pair `(const uint8_t *p, size_t n)`:

| Case | Behaviour |
|---|---|
| `n == 0` | `p` may be NULL and is never dereferenced. |
| `n > 0` and `p == NULL` | `EKI_ERR_NULL_POINTER` |

The same rule applies to outputs whose size is given by an input length: `ct_out` (`pt_len`),
`pt_out` (`ct_len`), `okm` (`okm_len`), and to `approver_public_keys` with `approver_count` as its
length (a count that is not 0 needs a pointer, even a count that is out of range).

Everything else must be non-NULL regardless of lengths: fixed-size inputs (the 16-byte `tag` of
`eki_aead_open`, `public_key`, `sig`, `request`, `approver_public_key`, and the KEM's `pk`, `sk`,
`ct`), fixed-size outputs, the `eki_ks *` handle, key id pointers, `config`, `label`, `path`, and
the `out` handle pointer of the open calls. The `tag` of both HMAC verify functions comes with
`tag_len` and follows the pair rule above. Two pointers may be NULL by design: the
`audit_log_path` of an `eki_ks_config_v2` (no audit log) and the `expected_head` of
`eki_audit_verify` (no comparison).

The caller's obligations, numbered as the SAFETY comments of `core-rs/src/ffi.rs` cite them:

- **C1, validity.** For each pointer and length pair, and each fixed-size parameter with its size
  as the length, the pointer is NULL or points to that many bytes inside one live allocation,
  readable for an input and writable for an output.
- **C2, duration.** That memory stays valid until the call returns, and nothing else (another
  thread included) writes it meanwhile, nor reads an output buffer.
- **C3, no overlap.** No output buffer overlaps any other buffer parameter. In-place AEAD is not
  supported.
- **C4, structs.** A non-NULL pointer to a struct or integer (`eki_key_id`, `eki_key_info`,
  `eki_key_info_v2`, `eki_ks_config`, `eki_ks_config_v2`, `eki_ks *`, `uint32_t`, `uint64_t`) is
  aligned for its type and valid for one value of it, initialised for an input. The string fields
  of a configuration are read only when `backend` is `EKI_KS_PKCS11` and the library has the
  PKCS#11 backend; otherwise they may hold any value. `approver_public_keys` is read only when
  `approver_count` is between 2 and `EKI_APPROVERS_MAX`, and then for `approver_count * 65` bytes.
- **C5, handles.** A non-NULL `eki_ks *` is a value an open call returned that has not been passed
  to `eki_ks_close`. `eki_ks_close` does not run at the same time as any other call on that
  handle, and the handle is not used after it.
- **C6, bounded strings.** A non-NULL `label` points to a NUL-terminated string or to at least 65
  readable bytes; the library reads up to the first NUL or 65 bytes, whichever comes first. The
  same holds with other bounds for `pkcs11_token_label` (33 bytes), `pkcs11_user_pin` (256 bytes),
  `audit_log_path` and the `path` of `eki_audit_verify` (4097 bytes). No NUL within the bound is
  `EKI_ERR_INVALID_ARGUMENT`.
- **C7, module path.** A non-NULL `pkcs11_module_path` of a PKCS#11 configuration points to a
  NUL-terminated string. The contract sets no maximum length; both libraries read to the NUL.

**Lengths above a documented maximum.** When a length exceeds the documented maximum of its
parameter (`EKI_AEAD_MAX_LEN` for `pt_len` and `ct_len`, `EKI_HKDF_MAX_INPUT_LEN` for `ikm_len`,
`salt_len` and `info_len`, `EKI_HKDF_MAX_OKM_LEN` for `okm_len`), C1 does not hold for it: the
buffer may be smaller than the length says. The call fails with `EKI_ERR_INVALID_ARGUMENT` without
reading or writing that buffer, and the Rust library never makes a slice over it (a slice longer
than its allocation is undefined behaviour even if no byte of it is read). The same applies to
an `approver_count` outside 2 to 8.

## Labels

A label is a NUL-terminated byte string of 1 to 64 bytes (`EKI_LABEL_MAX_LEN`), every byte in
`0x20..=0x7E` (printable ASCII). The library reads at most 65 bytes; if no NUL appears within them
the call fails with `EKI_ERR_INVALID_ARGUMENT`. Labels need not be unique; keys are identified by
their 16-byte id. A PKCS#11 token label follows the same rule with 1 to 32 bytes.

## Validation order

Every function checks its inputs in the same order, and the first failing step decides the status:

1. NULL checks on every pointer parameter, in parameter order (`ks` first). Fields of a
   configuration are NULL-checked after the selector, in field order, before any field's format.
2. Selector validity (`alg`, `backend`): an unknown value gives `EKI_ERR_INVALID_ARGUMENT`; a known
   value whose support is not compiled in gives `EKI_ERR_UNSUPPORTED`. A function that is not
   compiled in at all (the hybrid KEM without `pq`) returns `EKI_ERR_UNSUPPORTED` at this step, as
   does a dual-control or audit function on a handle opened without approvers or without a log.
3. Length, range and format checks, in parameter order: `EKI_ERR_INVALID_ARGUMENT`.
4. Store state: `EKI_ERR_KEY_NOT_FOUND`, `EKI_ERR_WRONG_KEY_TYPE`, `EKI_ERR_KEY_STATE`,
   `EKI_ERR_KEY_EXISTS`, `EKI_ERR_APPROVAL_REQUIRED`, following the per-function order below.
5. Cryptographic verification: `EKI_ERR_AUTH_FAILED`.
6. Internal failure of OpenSSL, the PKCS#11 module, the operating system or the file system:
   `EKI_ERR_BACKEND`.
7. A caught Rust panic or C++ exception: `EKI_ERR_INTERNAL`.

A PKCS#11 object that carries the requested id but is not a key this library can describe (a
foreign object, see [Foreign objects](#foreign-objects)) is `EKI_ERR_BACKEND` at the point where
the key would be described, which is inside step 4.

## Status codes

`eki_status` is a 32-bit enum. Values are stable and append-only: a value is never renumbered or
reused. Callers must be prepared for values they do not know; `eki_status_name` returns
`"EKI_STATUS_UNKNOWN"` for them.

| Value | Name | Meaning | Returned by |
|---|---|---|---|
| 0 | `EKI_OK` | Success; every output is fully written. | every status-returning function |
| 1 | `EKI_ERR_NULL_POINTER` | A required pointer is NULL, or a non-empty buffer has a NULL pointer. | every status-returning function |
| 2 | `EKI_ERR_INVALID_ARGUMENT` | Unknown selector, wrong length, value out of range, malformed label or path, unparseable public key, degenerate KEM input. | the stateless functions, the open calls, `eki_ks_generate`, `eki_ks_unwrap`, `eki_ks_hmac_sha256_verify`, `eki_ks_destroy_approve`, `eki_audit_verify`, the hybrid KEM |
| 3 | `EKI_ERR_BUFFER_TOO_SMALL` | Reserved for future variable-length outputs. | none in ABI 2 |
| 4 | `EKI_ERR_UNSUPPORTED` | The selector or function is known but not compiled in, or the handle was opened without the feature. | the open calls (PKCS#11 off), hybrid KEM (`pq` off), `eki_ks_destroy_request` and `eki_ks_destroy_approve` (no approvers), `eki_ks_audit_head` (no log) |
| 5 | `EKI_ERR_AUTH_FAILED` | AEAD tag, HMAC tag, ECDSA signature, AES-KW integrity, approval or audit log verification failed. | `eki_hmac_sha256_verify`, `eki_aead_open`, `eki_ecdsa_p256_verify`, `eki_ks_unwrap`, `eki_ks_hmac_sha256_verify`, `eki_ks_destroy_approve`, `eki_ks_open_v2`, `eki_audit_verify` |
| 6 | `EKI_ERR_KEY_NOT_FOUND` | No object in the store carries the given key id, or no pending destroy request has the given value. | every key store function that takes a key id, `eki_ks_destroy_approve` |
| 7 | `EKI_ERR_KEY_EXISTS` | The key id requested for an unwrapped key is already in use. | `eki_ks_unwrap` |
| 8 | `EKI_ERR_WRONG_KEY_TYPE` | The key exists but its algorithm does not allow the operation. | `eki_ks_get_public_key`, `eki_ks_sign`, `eki_ks_hmac_sha256`, `eki_ks_hmac_sha256_verify`, `eki_ks_wrap`, `eki_ks_unwrap` |
| 9 | `EKI_ERR_BACKEND` | OpenSSL, the PKCS#11 module, the operating system or the audit log file failed; a foreign PKCS#11 object; never caused by a malformed argument. | every status-returning function; stateless ones only when an algorithm cannot be fetched or memory cannot be allocated |
| 10 | `EKI_ERR_INTERNAL` | A panic or exception was caught at the boundary, or an internal invariant was violated. | every status-returning function |
| 11 | `EKI_ERR_KEY_STATE` | The key's lifecycle state does not permit the operation. | `eki_ks_get_public_key`, `eki_ks_sign`, `eki_ks_hmac_sha256`, `eki_ks_hmac_sha256_verify`, `eki_ks_wrap`, `eki_ks_unwrap`, `eki_ks_rotate` |
| 12 | `EKI_ERR_APPROVAL_REQUIRED` | The handle has dual control: destroy needs two approvals. | `eki_ks_destroy` |

## Types and constants

Input selectors (`eki_aead_alg`, `eki_key_alg`, `eki_ks_backend`) are plain `int32_t` typedefs
with `#define` values rather than C enums, so any value a C caller passes is representable on the
Rust side and an unknown one is rejected with a status instead of being undefined behaviour.
`eki_key_state` is an `int32_t` the library writes; it holds one of the three state values, or 0
in a zero-filled output. Before C23, `eki_status` is an `int32_t` typedef in C; in C++ and C23 it
is the enum with `int32_t` as its underlying type.

| Selector | Values |
|---|---|
| `eki_aead_alg` | `EKI_AEAD_AES_256_GCM = 1`, `EKI_AEAD_CHACHA20_POLY1305 = 2` |
| `eki_key_alg` | `EKI_KEY_AES_256 = 1` (32-byte secret, KEK, wrappable), `EKI_KEY_HMAC_SHA256 = 2` (32-byte secret, wrappable), `EKI_KEY_ECDSA_P256 = 3` (key pair, not wrappable) |
| `eki_ks_backend` | `EKI_KS_SOFTWARE = 1`, `EKI_KS_PKCS11 = 2` |
| `eki_key_state` | `EKI_KEY_STATE_ACTIVE = 1`, `EKI_KEY_STATE_RETIRED = 2`, `EKI_KEY_STATE_REVOKED = 3` |

| Constant | Value | Meaning |
|---|---|---|
| `EKI_ABI_VERSION` | 2 | ABI version, see [ABI stability and versioning](#abi-stability-and-versioning) |
| `EKI_HMAC_SHA256_LEN` | 32 | HMAC-SHA256 tag |
| `EKI_AEAD_KEY_LEN` | 32 | AEAD key |
| `EKI_AEAD_NONCE_LEN` | 12 | AEAD nonce |
| `EKI_AEAD_TAG_LEN` | 16 | AEAD tag |

Structs: `eki_key_id` (16 bytes), `eki_key_info` (`alg`, `label[65]`), `eki_key_info_v2` (`alg`,
`state`, `label[65]`), `eki_ks_config` (`backend` and the three PKCS#11 strings) and
`eki_ks_config_v2` (the same fields, then `audit_log_path`, `approver_public_keys`,
`approver_count`). `eki_ks` is opaque. `EKI_API` marks every function for export (default
visibility with GCC and Clang); `EKICORE_H` is the include guard.

## Per-function contract

"Failures in order" lists the statuses beyond step 1 (NULL checks, which every function performs
in parameter order) in the order they are checked. "Missing" means `EKI_ERR_KEY_NOT_FOUND`;
"foreign" means a foreign PKCS#11 object, `EKI_ERR_BACKEND`.

### Metadata

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_abi_version` | none | returns `EKI_ABI_VERSION` (2) | none |
| `eki_version` | none | static string `"ekicore-cpp <semver>"` or `"ekicore-rs <semver>"` | none |
| `eki_status_name` | `int32_t status` | static name such as `"EKI_ERR_AUTH_FAILED"`; never NULL | unknown value returns `"EKI_STATUS_UNKNOWN"` |

### Stateless primitives

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_hmac_sha256` | `key[key_len]`, `msg[msg_len]` | `out[32]` | `key_len == 0` → INVALID_ARGUMENT |
| `eki_hmac_sha256_verify` | `key[key_len]`, `msg[msg_len]`, `tag[tag_len]` | none | `key_len == 0` → INVALID_ARGUMENT; `tag_len != 32` → INVALID_ARGUMENT; constant-time mismatch → AUTH_FAILED |
| `eki_hkdf_sha256` | `ikm[ikm_len]`, `salt[salt_len]`, `info[info_len]` | `okm[okm_len]` | `ikm_len` 0 or > 32768; `salt_len` > 32768; `info_len` > 32768; `okm_len` 0 or > 8160 → INVALID_ARGUMENT, in that order. `salt_len == 0` means the RFC 5869 default salt. |
| `eki_aead_seal` | `alg`, `key[key_len]`, `nonce[nonce_len]`, `aad[aad_len]`, `pt[pt_len]` | `ct_out[pt_len]`, `tag_out[16]` | unknown `alg` → INVALID_ARGUMENT; `key_len != 32`; `nonce_len != 12`; `pt_len > EKI_AEAD_MAX_LEN` → INVALID_ARGUMENT. `aad_len` and `pt_len` may be 0. |
| `eki_aead_open` | `alg`, `key[key_len]`, `nonce[nonce_len]`, `aad[aad_len]`, `ct[ct_len]`, `tag[16]` | `pt_out[ct_len]` | as seal, with `ct_len`; then tag mismatch → AUTH_FAILED. `ct_len == 0` with a valid tag is OK. |
| `eki_ecdsa_p256_verify` | `public_key[65]`, `msg[msg_len]`, `sig[64]` | none | `public_key[0] != 0x04` → INVALID_ARGUMENT; key does not parse (off curve, coordinate ≥ p) → INVALID_ARGUMENT; `r` or `s` zero or ≥ n, or the signature does not verify → AUTH_FAILED. High-s signatures are accepted. |

Stateless functions return `EKI_ERR_BACKEND` only when an algorithm cannot be fetched or memory
cannot be allocated, never for a failure derived from the input.

### Key store

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_ks_open` | `config` | `*out` (NULL on failure) | as `eki_ks_open_v2` with no audit log and no approvers: unknown `backend` → INVALID_ARGUMENT; PKCS#11 not compiled in → UNSUPPORTED; PKCS#11 only: `pkcs11_module_path`, `pkcs11_token_label`, `pkcs11_user_pin` NULL (field order) → NULL_POINTER; token label not 1..=32 printable bytes, PIN not 1..=255 bytes → INVALID_ARGUMENT; module load, initialisation, slot lookup, session or login failure → BACKEND. The software backend ignores the PKCS#11 fields. |
| `eki_ks_close` | `ks` (may be NULL) | none | none; writes the `close` record when the handle has a log, and ignores a failure to write it |
| `eki_ks_last_error_message` | `ks`, `buf[buf_len]` | message text, returns its full length | see [Last error message](#last-error-message) |
| `eki_ks_generate` | `ks`, `alg`, `label` | `id_out` (16 random bytes) | unknown `alg` → INVALID_ARGUMENT; label format → INVALID_ARGUMENT; the random id is already taken → BACKEND; backend failure → BACKEND |
| `eki_ks_get_info` | `ks`, `id` | `info_out` (`alg`, label NUL-padded through byte 64) | missing; foreign. Any algorithm, any state. |
| `eki_ks_get_public_key` | `ks`, `id` | `out[65]` | missing; foreign; not ECDSA_P256 → WRONG_KEY_TYPE; REVOKED → KEY_STATE |
| `eki_ks_sign` | `ks`, `id`, `msg[msg_len]` | `sig_out[64]` | missing; foreign; not ECDSA_P256 → WRONG_KEY_TYPE; not ACTIVE → KEY_STATE |
| `eki_ks_hmac_sha256` | `ks`, `id`, `msg[msg_len]` | `out[32]` | missing; foreign; not HMAC_SHA256 → WRONG_KEY_TYPE; not ACTIVE → KEY_STATE |
| `eki_ks_wrap` | `ks`, `kek_id`, `key_id` | `out[40]` | KEK missing; key missing; KEK foreign; KEK not AES_256 → WRONG_KEY_TYPE; key foreign; key not AES_256 or HMAC_SHA256 → WRONG_KEY_TYPE; KEK not ACTIVE → KEY_STATE; key REVOKED → KEY_STATE. Wrapping a key under itself is allowed. |
| `eki_ks_unwrap` | `ks`, `kek_id`, `blob[blob_len]`, `alg`, `label`, `id` | a new ACTIVE key with the given id | unknown `alg` → INVALID_ARGUMENT; `blob_len != 40` → INVALID_ARGUMENT; `alg == ECDSA_P256` → INVALID_ARGUMENT; label format → INVALID_ARGUMENT; KEK missing; KEK foreign; KEK not AES_256 → WRONG_KEY_TYPE; KEK REVOKED → KEY_STATE; `id` already carried by any object, foreign ones included → KEY_EXISTS; AES-KW integrity → AUTH_FAILED |
| `eki_ks_destroy` | `ks`, `id` | none | missing; handle with approvers → APPROVAL_REQUIRED (nothing changes). Any algorithm, any state, foreign objects included; destroys every object with that id. |

The wrapped-key format is RFC 3394 AES key wrap of the 32-byte key value under a 256-bit KEK: 40
bytes, no header. It is the same as PKCS#11 `CKM_AES_KEY_WRAP`, OpenSSL `EVP_aes_256_wrap` and
RustCrypto `aes-kw`. The algorithm, label and id are not inside the blob; the caller supplies them
to `eki_ks_unwrap`.

### Hybrid KEM (optional)

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_hybrid_kem_keygen` | none | `pk_out[1216]`, `sk_out[96]` | not compiled in → UNSUPPORTED |
| `eki_hybrid_kem_encap` | `pk[1216]` | `ct_out[1120]`, `ss_out[32]` | not compiled in → UNSUPPORTED; all-zero X25519 shared secret → INVALID_ARGUMENT; ML-KEM encapsulation key fails the FIPS 203 modulus check → INVALID_ARGUMENT |
| `eki_hybrid_kem_decap` | `sk[96]`, `ct[1120]` | `ss_out[32]` | not compiled in → UNSUPPORTED; all-zero X25519 shared secret → INVALID_ARGUMENT. ML-KEM decapsulation never fails: implicit rejection yields a different secret. |

Layouts: `pk = x25519_pk(32) || mlkem768_ek(1184)`; `sk = x25519_sk(32) || mlkem768_seed d||z (64)`;
`ct = x25519_ephemeral_pk(32) || mlkem768_ct(1088)`. Decapsulation rebuilds `pk` from `sk`. The
combiner is

```
ss = HKDF-SHA256(ikm  = ss_x25519 || ss_mlkem,
                 salt = "",
                 info = "ekibridge-hybrid-x25519-mlkem768-v1" || ct || pk,
                 L    = 32)
```

### Opening a store with ABI 2

```c
eki_status eki_ks_open_v2(const struct eki_ks_config_v2 *config, struct eki_ks **out);
```

`eki_ks_open(config)` is this function with `audit_log_path` NULL, `approver_public_keys` NULL
and `approver_count` 0; both share one body in each library. The checks, in order:

1. `config`, `out` NULL → NULL_POINTER.
2. `backend` unknown → INVALID_ARGUMENT; `EKI_KS_PKCS11` without PKCS#11 support → UNSUPPORTED.
3. NULL fields, in field order → NULL_POINTER: the three PKCS#11 strings (PKCS#11 backend only),
   then `approver_public_keys` when `approver_count` is not 0 (also when the count is out of
   range). A NULL `audit_log_path` is not an error.
4. Malformed fields, in field order → INVALID_ARGUMENT: token label, PIN (PKCS#11 backend only);
   `audit_log_path` empty or without a NUL within 4097 bytes; `approver_count` not 0 and not 2 to
   8; an approver key that is not a valid SEC1 uncompressed P-256 point, or a key given twice.
   With `approver_count` 0 the keys are not read.
5. The backend is opened: any failure → BACKEND.
6. The audit log is opened (created with mode 0600 if missing) and locked: an existing log that
   fails [verification](#verification) → AUTH_FAILED, and the file is left byte for byte
   unchanged; a log that cannot be opened, created, locked or read, or is not a regular file →
   BACKEND. A second handle on a log that is open, in the same process or another, fails here with
   BACKEND.
7. The `open` record is written: failure → BACKEND.

On any failure nothing stays open and `*out` is NULL. There is no handle yet, so the reason of a
failure is not available through `eki_ks_last_error_message`.

### Lifecycle functions

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_ks_get_info_v2` | `ks`, `id` | `info_out` (`alg`, `state`, label NUL-padded through byte 64) | missing; foreign. Any state. |
| `eki_ks_rotate` | `ks`, `old_id` | `new_id_out` | missing; foreign; not ACTIVE → KEY_STATE; the random id is already taken → BACKEND; creating the new key fails → BACKEND; retiring the old key fails → BACKEND, and the new key is destroyed again. Any algorithm. |
| `eki_ks_revoke` | `ks`, `id` | none | missing; foreign. Revoking a REVOKED key returns OK and calls no backend. |
| `eki_ks_hmac_sha256_verify` | `ks`, `id`, `msg[msg_len]`, `tag[tag_len]` | none | `tag_len != 32` → INVALID_ARGUMENT; missing; foreign; not HMAC_SHA256 → WRONG_KEY_TYPE; REVOKED → KEY_STATE; constant-time mismatch → AUTH_FAILED |

The new key of `eki_ks_rotate` has the old key's algorithm and label, fresh key material and a
fresh random id; it starts ACTIVE and the old key becomes RETIRED.

### Audit functions

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_ks_audit_head` | `ks` | `hash_out[32]`, `*seq_out` | handle without a log → UNSUPPORTED. Not logged. |
| `eki_audit_verify` | `path`, `expected_head[32]` or NULL | `*records_out` | `path` empty or without a NUL within 4097 bytes → INVALID_ARGUMENT; the file cannot be opened or read, or is not a regular file → BACKEND; any deviation from the format or the chain, or a last hash other than `expected_head` → AUTH_FAILED |

`eki_ks_audit_head` writes the hash and `seq` of the last record the handle's log holds. Kept
outside the log, the hash lets `eki_audit_verify` detect a log whose tail was cut off, which the
chain alone cannot show. For an empty file the expected head is 32 zero bytes.

### Dual control functions

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_ks_destroy_request` | `ks`, `id` | `request_out[32]` | handle without approvers → UNSUPPORTED; missing (a foreign object counts as present); random source failure → BACKEND |
| `eki_ks_destroy_approve` | `ks`, `request[32]`, `approver_public_key[65]`, `sig[64]` | `*remaining_out` | handle without approvers → UNSUPPORTED; approver key not a valid P-256 point → INVALID_ARGUMENT; no pending request with this value → KEY_NOT_FOUND; key not among the approvers → AUTH_FAILED; signature does not verify → AUTH_FAILED; completing approval: key gone → KEY_NOT_FOUND (request removed), destroy fails → BACKEND (request kept with its earlier approvals) |

The protocol is in [Dual control](#dual-control).

## Outputs on error

On any status other than `EKI_OK`, every non-NULL output is zero-filled:

- fixed-size outputs over their full size (`request_out`, `hash_out`, `new_id_out`, ...);
- `info_out` over `sizeof(eki_key_info)` or `sizeof(eki_key_info_v2)`, so a failed
  `eki_ks_get_info_v2` leaves `state` 0, which is not a state;
- integer outputs (`*remaining_out`, `*seq_out`, `*records_out`) set to 0;
- `*out` of the open calls set to NULL;
- a variable-length output over its declared length, but only if that length is within its valid
  range (`okm_len` in 1..=8160, `pt_len` / `ct_len` ≤ `EKI_AEAD_MAX_LEN`); otherwise it is left
  untouched.

On `EKI_OK` every output is fully written, and the `label` of `eki_key_info` and
`eki_key_info_v2` is NUL-padded through byte 64. Struct padding bytes are unspecified; compare
fields, never raw struct bytes.

`eki_aead_open` deserves a note: OpenSSL's GCM decryption writes plaintext before it checks the tag,
so the C++ library must zero `pt_out` on failure. RustCrypto leaves the buffer untouched on failure;
the Rust library zeroes it anyway, so the two are indistinguishable.

## Last error message

`size_t eki_ks_last_error_message(const eki_ks *ks, char *buf, size_t buf_len)` follows the
`snprintf` convention: it writes at most `buf_len - 1` bytes plus a NUL and returns the full length
of the message, excluding the NUL. `buf == NULL` is treated as `buf_len == 0`. With `ks == NULL` it
writes `""` if there is room and returns 0.

Every store call except `eki_ks_last_error_message` and `eki_ks_close` resets the message to `""`
on entry, also when it then fails a NULL check. A `EKI_ERR_BACKEND` failure always leaves a
non-empty message: the `CKR_*` name with the PKCS#11 function, the OpenSSL error string, the
operating system error of the audit log, or a sentence such as the one for a foreign object.
Other failures may leave one; `EKI_ERR_AUTH_FAILED` from a PKCS#11 unwrap carries
`C_UnwrapKey failed: CKR_...` in both libraries. Failures inside the open calls and of
`eki_audit_verify` have no handle and report a status only. Message text is diagnostic and differs
between the two libraries.

## Thread safety

- Stateless functions and `eki_audit_verify` are thread-safe and reentrant.
- An `eki_ks` handle serialises all operations with an internal lock and may be shared between
  threads. The last-error message reflects the most recent operation on that handle by any thread.
  Audit records of one handle are written in the order the operations take the lock.
- `eki_ks_close` must not race with any other call on the same handle.
- A poisoned Rust mutex (a panic while it was held) is recovered rather than propagated. C++
  `std::mutex` cannot be poisoned.
- PKCS#11 initialisation and login are per process. Two ekicore libraries loaded into one process
  must not hold PKCS#11 stores open at the same time; see the
  [threat model](threat-model.md#pkcs11-specifics).
- The audit log lock is an `flock` lock on the open file, so it excludes a second handle in the
  same process as well as in another process. Pending destroy requests belong to one handle and
  are not shared with other handles on the same token.

## Key states

Every key has one of three states. Generated and unwrapped keys start ACTIVE. `eki_ks_rotate`
moves a key from ACTIVE to RETIRED; `eki_ks_revoke` moves a key from either state to REVOKED. No
call moves a key back.

| Operation | ACTIVE | RETIRED | REVOKED |
|---|---|---|---|
| `eki_ks_get_info`, `eki_ks_get_info_v2` | yes | yes | yes |
| `eki_ks_get_public_key` | yes | yes | KEY_STATE |
| `eki_ks_sign` | yes | KEY_STATE | KEY_STATE |
| `eki_ks_hmac_sha256` (make a tag) | yes | KEY_STATE | KEY_STATE |
| `eki_ks_hmac_sha256_verify` (check a tag) | yes | yes | KEY_STATE |
| `eki_ks_wrap`, as the KEK | yes | KEY_STATE | KEY_STATE |
| `eki_ks_wrap`, as the key wrapped | yes | yes | KEY_STATE |
| `eki_ks_unwrap`, as the KEK | yes | yes | KEY_STATE |
| `eki_ks_rotate`, as the old key | yes | KEY_STATE | KEY_STATE |
| `eki_ks_revoke` | yes | yes | yes (no change) |
| `eki_ks_destroy`, `eki_ks_destroy_request` | yes | yes | yes |

A retired key may still check or recover what it once protected and may not protect anything new.
A revoked key may only be described, revoked again, destroyed and have its destruction requested.
A key unwrapped under a retired KEK starts ACTIVE. In the software backend the state lives in the
handle; in the PKCS#11 backend it lives in the token, so a state set through one handle or one
library is seen by every other.

## PKCS#11 object mapping and lifecycle

Both libraries store keys in the token with the same objects and attributes, so each can use the
keys the other created.

| Key | Objects | Mechanisms |
|---|---|---|
| AES-256 | one `CKO_SECRET_KEY`, `CKK_AES`, `CKA_VALUE_LEN` 32 at generation | `CKM_AES_KEY_GEN`; `CKM_AES_KEY_WRAP` for wrap and unwrap |
| HMAC-SHA256 | one `CKO_SECRET_KEY`, `CKK_GENERIC_SECRET`, `CKA_VALUE_LEN` 32 at generation | `CKM_GENERIC_SECRET_KEY_GEN`; `CKM_SHA256_HMAC` for tags and their verification |
| ECDSA P-256 | `CKO_PRIVATE_KEY` and `CKO_PUBLIC_KEY`, `CKK_EC`, `CKA_EC_PARAMS` the P-256 OID | `CKM_EC_KEY_PAIR_GEN`; `CKM_ECDSA` over a SHA-256 digest computed in the library |

Every object carries `CKA_TOKEN` TRUE, `CKA_ID` the 16 id bytes and `CKA_LABEL` the label without
its NUL; `CKA_PRIVATE` is TRUE except on the public half of a key pair. Secret keys are
`CKA_SENSITIVE` TRUE and `CKA_EXTRACTABLE` TRUE (so that they can be wrapped); the private EC key
is `CKA_SENSITIVE` TRUE and `CKA_EXTRACTABLE` FALSE. Key values are generated inside the token and
never enter the library's memory. The unwrap template has no `CKA_VALUE_LEN`; the length comes from
the blob. The public key is read from `CKA_EC_POINT`.

**State in usage attributes.** The lifecycle state is held in two groups of usage attributes:

| Algorithm | "protect" group | "check" group |
|---|---|---|
| AES-256 | `CKA_WRAP`, `CKA_ENCRYPT` | `CKA_UNWRAP`, `CKA_DECRYPT` |
| HMAC-SHA256 | `CKA_SIGN` | `CKA_VERIFY` |
| ECDSA P-256 | `CKA_SIGN` of the private object | `CKA_VERIFY` of the public object |

Both groups TRUE is ACTIVE, protect FALSE with check TRUE is RETIRED, both FALSE is REVOKED. A
transition clears the protect group first and then, for REVOKED, the check group, each with one
`C_SetAttributeValue` per object; for a key pair the private object is changed first. Between the
two calls the key is RETIRED, a state of the table. Only these attributes are read: SoftHSM2 sets
usage flags outside the templates to TRUE by default (for example `CKA_SIGN` of an AES key), so
they say nothing about the state. The token then refuses what the state forbids, although the
library refuses first. SoftHSM2 2.7.0 accepts setting a cleared flag back to TRUE, so only the
library keeps the transitions one-way; any program with the user PIN can move a key back.

Every operation looks its objects up again by `CKA_ID` (`C_FindObjects`); object handles are not
kept between calls, because another session or process may destroy or replace the objects in
between. When that happens between the store's checks and the operation, the operation is a backend
failure.

### Foreign objects

An object that carries a 16-byte id this library looks up, but that does not form one of the
shapes above, is foreign: a lone half of a key pair, two secret keys with one id, a key type or
curve other than the table's, a `CKA_LABEL` that is not a valid label, a usage-flag combination
outside the state table, or a flag that cannot be read. A foreign object:

- makes `eki_ks_get_info`, `eki_ks_get_info_v2`, `eki_ks_get_public_key`, `eki_ks_sign`,
  `eki_ks_hmac_sha256`, `eki_ks_hmac_sha256_verify`, `eki_ks_rotate` and `eki_ks_revoke` fail with
  `EKI_ERR_BACKEND` and a message saying the object cannot be described;
- fails `eki_ks_wrap` with `EKI_ERR_BACKEND` as the KEK or as the key, after both ids were found to
  exist (a missing key wins over a foreign one);
- fails `eki_ks_unwrap` as the KEK with `EKI_ERR_BACKEND`, and occupies its id: unwrapping to the
  id of a foreign object is `EKI_ERR_KEY_EXISTS`;
- can be destroyed with `eki_ks_destroy`, which destroys every object with that id, and can have
  its destruction requested and approved.

## Audit log

A handle opened with an `audit_log_path` appends one record per logged call to that file.

### Record format

A record is one line of ASCII, terminated by `\n`, with this fixed grammar and no whitespace:

```
{"seq":N,"time":"YYYY-MM-DDTHH:MM:SSZ","op":"OP","key":"ID","key2":"ID","status":S,"prev":"H","hash":"H"}
```

| Field | Value |
|---|---|
| `seq` | 1 for the first record of the file, then one more per record; canonical decimal (no sign, no leading zero), at most 20 digits |
| `time` | UTC time of the call, truncated to the second; a real calendar date in 1970..9999, hour < 24, minute and second < 60 |
| `op` | one of the 14 names below |
| `key`, `key2` | 32 lowercase hexadecimal digits of a key id, or empty |
| `status` | the `eki_status` the call returned, canonical decimal 0 to 12 |
| `prev` | 64 lowercase hexadecimal digits: the `hash` of the previous record, 64 zeros for the first |
| `hash` | 64 lowercase hexadecimal digits: SHA-256 over every byte of the line before `,"hash":` |

Each hash covers the previous one through `prev`, so the records form a chain. The longest record
the libraries can write is 325 bytes including its `\n`; the verifier accepts lines of at most 512
bytes including the `\n`.

| `op` | Call | `key` | `key2` |
|---|---|---|---|
| `open` | `eki_ks_open_v2` | empty | empty |
| `close` | `eki_ks_close` | empty | empty |
| `generate` | `eki_ks_generate` | the new id on success, else empty | empty |
| `unwrap` | `eki_ks_unwrap` | the `id` given | the KEK |
| `rotate` | `eki_ks_rotate` | the old id | the new id on success, else empty |
| `revoke` | `eki_ks_revoke` | the id | empty |
| `destroy` | `eki_ks_destroy` | the id | empty |
| `destroy_request` | `eki_ks_destroy_request` | the id | empty |
| `destroy_approve` | `eki_ks_destroy_approve` | the key of the request, empty if no request matched | empty |
| `sign` | `eki_ks_sign` | the id | empty |
| `hmac` | `eki_ks_hmac_sha256` | the id | empty |
| `hmac_verify` | `eki_ks_hmac_sha256_verify` | the id | empty |
| `wrap` | `eki_ks_wrap` | the key wrapped | the KEK |
| `get_public_key` | `eki_ks_get_public_key` | the id | empty |

The `open` and `close` records have status 0. Every other record carries the status the call
returns, failures included. A call that fails its NULL checks is not logged. Not logged at all:
`eki_ks_get_info`, `eki_ks_get_info_v2`, `eki_ks_last_error_message`, `eki_ks_audit_head`, the
stateless functions and `eki_audit_verify`. A handle opened on an existing log continues its
chain: the first new record has the next `seq` and the last hash as `prev`.

### Writing

- The file is opened for appending, created with mode 0600 when missing, verified, and locked
  with `flock(LOCK_EX | LOCK_NB)` for the life of the handle.
- The path must name a regular file; a symbolic link is followed. A directory, a device, a FIFO
  or a socket is `EKI_ERR_BACKEND`, for the open call and for `eki_audit_verify` alike, and
  nothing is read from it or written to it. The type is that of the open file (`fstat`), checked
  before the first read (in the open call, after the lock). A FIFO does not make either call wait
  for a writer, except in the race described under [Known differences](#known-differences).
- Each record is written with a single `write` and flushed to stable storage before the call
  returns: with `fcntl(F_FULLFSYNC)` on Apple platforms, where `fsync` leaves the data in the
  drive's cache, and with `fsync` elsewhere (`File::sync_data` in the Rust library, which is
  `F_FULLFSYNC` on Apple platforms and `fdatasync` on Linux). The C++ library falls back to
  `fsync` when a file system rejects `F_FULLFSYNC`.
- If a record cannot be written in full, the call returns `EKI_ERR_BACKEND` even if the operation
  succeeded, the file is truncated back to its previous length, and what the operation did is
  undone where that is possible: a key it created (generate, unwrap, rotate) is destroyed again and
  the pending destroy requests are restored. A destroyed key and a state change (revoke, the
  retiring of the old key in rotate) cannot be undone; the last-error message says which happened.
- If the truncation fails too, the handle marks its log broken and fails every later logged call
  with `EKI_ERR_BACKEND` without writing, because a record after a partial line could never verify.
- A panic or exception inside a logged operation is recorded with status 10
  (`EKI_ERR_INTERNAL`), the status the barrier then returns. The contract leaves this open; both
  libraries do it.

### Verification

`eki_audit_verify` and the open check accept a file only if:

- it is a regular file (anything else is `EKI_ERR_BACKEND`, not `EKI_ERR_AUTH_FAILED`);
- every line is a record of exactly the grammar above, at most 512 bytes with its `\n`;
- the `seq` values are 1, 2, 3, ... in order;
- each `prev` is the previous record's `hash` (64 zeros for the first) and each `hash` is the
  SHA-256 of its line before `,"hash":`;
- `op`, `status` and `time` are valid as listed above, and the numbers are canonical;
- the file ends with `\n` after the last record. An empty file is a valid log with no records.
  CRLF line ends, a trailing empty line or a missing final `\n` fail.

The verifier extracts only the fields a writer chooses (`time`, `op`, `key`, `key2`, `status`),
formats the line those fields must give at that position of the chain, and requires the file to
hold exactly those bytes. Every deviation is therefore one failure, `EKI_ERR_AUTH_FAILED`. With
`expected_head` the hash of the last record must also equal it (32 zero bytes for an empty file).
The order of `time` values is not checked. The verifier takes no lock; it checks the bytes it
reads at that moment. A log written by one library verifies in the other, and either library can
continue it.

The chain shows that records were not changed, inserted, removed or reordered, except at the end:
a log cut after any complete record still verifies. Keeping the head returned by
`eki_ks_audit_head` elsewhere closes that gap. Anyone who can write the file can also replace it
with a different, internally consistent chain; the chain is not signed.

## Dual control

A handle opened with `approver_count` 2 to 8 has dual control of destroy. `eki_ks_destroy`
then returns `EKI_ERR_APPROVAL_REQUIRED` and changes nothing; a key is destroyed only through this
protocol:

1. `eki_ks_destroy_request(ks, id, request)` writes 32 random bytes to `request` and remembers
   them for the key. A new request for the same key replaces the old one and drops its approvals.
2. Each approver signs, with the private key of one of the configured approver public keys, the
   68-byte message

   ```
   "ekibridge-destroy-v1" (20 ASCII bytes) || request (32 bytes) || key id (16 bytes)
   ```

   with ECDSA P-256 over SHA-256, as a 64-byte `r || s` signature.
3. `eki_ks_destroy_approve(ks, request, approver_public_key, sig, &remaining)` records the
   approval and writes the number of approvals still needed. A second approval by the same
   approver changes nothing and still returns 1. The approval of a second, different approver
   destroys the key (every object with its id), removes the request and returns 0.

Requests live in the handle that made them and vanish when it is closed; they cannot be approved
through another handle. An approval does not need the approver's private key in the library: any
P-256 signer can produce it, for example a key in another key store (the conformance tests use the
other library's software store). The approver keys are fixed when the handle is opened.

## Secret handling

| | Rust (`libekicore_rs`) | C++ (`libekicore`) |
|---|---|---|
| Software store keys | `secrecy::SecretBox`, wiped on destroy and on close; ECDSA keys are `p256` signing keys, wiped on drop | `secret_buffer`: page-aligned `mmap` memory, `OPENSSL_cleanse` on destruction, non-copyable; ECDSA keys are an `EVP_PKEY` in OpenSSL's memory, freed (and cleared by OpenSSL) on destroy |
| Cipher state | `aes-gcm`, `aes-kw`, `chacha20poly1305`, `poly1305`, `sha2`, `ml-kem` built with `zeroize` | `EVP_CIPHER_CTX` and friends, freed by OpenSSL |
| Memory locking | none | `mlock` of `secret_buffer` pages, best effort, behind `EKI_MLOCK` (on by default) |
| PKCS#11 PIN copy | zeroizing heap copy, wiped after login | `secret_buffer` copy, wiped after login |
| Randomness | `getrandom` (operating system) | `RAND_priv_bytes` for secrets, `RAND_bytes` for ids and requests |

With the PKCS#11 backend, secret and private keys are generated inside the token with
`CKA_SENSITIVE=TRUE`; their values never enter the library's memory.

What is not wiped:

- Rust: temporaries inside the RustCrypto crates that are not built to wipe them leave copies on
  the stack: the padded HMAC key block, the HKDF pseudorandom key, the GCM counter block and tag
  temporaries, the AES key wrap scratch block, ECDSA signing temporaries and the RFC 6979 state,
  candidate scalars of `p256` key generation, moved copies of signing keys, and intermediates of
  X25519 and ML-KEM. Memory is not locked, so any of it can reach swap.
- C++: the `EVP_PKEY` of a software ECDSA key is not in locked memory, and OpenSSL's internal
  copies (expanded key schedules, digest state) are cleared by OpenSSL when freed, not under the
  library's control. Copies outside `secret_buffer` are not covered, nor is the stack.
- Both: caller buffers (keys passed to stateless functions, plaintext, shared secrets, the PIN in
  the configuration) are the caller's to wipe. Core dumps are not disabled.

## Panic and exception barriers

Nothing but a status crosses the boundary. Every Rust `extern "C"` function runs its body inside
`catch_unwind`; every C++ `extern "C"` function wraps its body in `try { ... } catch (...)`. A
caught panic or exception becomes `EKI_ERR_INTERNAL`, with outputs zeroed as above.
`eki_ks_last_error_message` and `eki_ks_close` return no status and contain a panic or exception
the same way. The Rust release profile keeps `panic = "unwind"` so that panics can be caught at
all; under `panic = "abort"` a panic would terminate the host process. A Rust panic payload whose
destructor panics again is dropped a bounded number of times and then leaked rather than unwound.

## ABI stability and versioning

- `eki_abi_version()` returns `EKI_ABI_VERSION`, currently 2. It changes only for an incompatible
  change; additions that keep every existing declaration and behaviour do not change it.
- ABI 1 to 2: every ABI 1 declaration is unchanged, and the additions are nine functions
  (`eki_ks_open_v2`, `eki_ks_get_info_v2`, `eki_ks_rotate`, `eki_ks_revoke`,
  `eki_ks_hmac_sha256_verify`, `eki_ks_destroy_request`, `eki_ks_destroy_approve`,
  `eki_ks_audit_head`, `eki_audit_verify`), the types `eki_ks_config_v2`, `eki_key_info_v2` and
  `eki_key_state`, four length constants, the three state values and two status values. The
  number moved because ABI 1 functions may now answer differently: `eki_ks_sign`,
  `eki_ks_hmac_sha256`, `eki_ks_get_public_key`, `eki_ks_wrap` and `eki_ks_unwrap` return
  `EKI_ERR_KEY_STATE` (a value ABI 1 did not have) for a key that is retired or revoked, which a
  PKCS#11 key can be when another handle or program changed it, and `eki_ks_destroy` returns
  `EKI_ERR_APPROVAL_REQUIRED` on a handle with approvers. A caller written for ABI 1 should check
  for 2 deliberately rather than accept it.
- `eki_status` values are append-only.
- `eki_version()` returns `"<impl> <semver>"` where `<impl>` is `ekicore-cpp` or `ekicore-rs` and
  the semver equals the CMake project version and the Cargo package version.
- Optional features (`pkcs11`, `pq`) gate function bodies only, never declarations, so the header
  and the exported symbol set are the same in every build. A disabled function performs its NULL
  checks and returns `EKI_ERR_UNSUPPORTED`.
- Only `eki_*` symbols are exported, 32 of them
  ([`scripts/check-exports.sh`](../scripts/check-exports.sh)).

## Known limitations

- The wrapped-key blob does not authenticate its metadata (algorithm, label, id); see the
  [threat model](threat-model.md#limits).
- Pending destroy requests live only as long as the handle that made them, with either backend.
- The PKCS#11 PIN is passed as a NUL-terminated C string and lives in caller memory for the
  duration of the open call.
- `EKI_ERR_BUFFER_TOO_SMALL` is reserved and never returned in ABI 2.
- Signatures produced by the two libraries are not byte-comparable: OpenSSL and SoftHSM2 use random
  nonces, RustCrypto `p256` uses RFC 6979 deterministic nonces. Signing is checked by
  cross-verification only.
- PKCS#11: every failure of `C_UnwrapKey` is reported as `EKI_ERR_AUTH_FAILED`, because SoftHSM2
  reports a wrong RFC 3394 integrity value as `CKR_GENERAL_ERROR`, which cannot be told apart from
  other causes; the last-error message names the code.
- PKCS#11: `CKA_VALUE_LEN` is never read, so an AES key of another length created by another
  program is described as `EKI_KEY_AES_256`.
- PKCS#11: the configured token label is compared blank-padded to 32 bytes, as `CK_TOKEN_INFO`
  holds it, so trailing blanks in the configured label are not significant.
- PKCS#11: a login that the module answers with `CKR_USER_ALREADY_LOGGED_IN` counts as success,
  so a wrong PIN is not detected while another handle of the same process is logged in to the
  token.
- PKCS#11: the one-way state transitions are enforced by the library, not by the token (see
  above).
- The audit log records calls through one handle only. It is not signed; its integrity rests on
  the chain plus a head kept elsewhere, and its durability on the file system honouring the flush
  (`F_FULLFSYNC` or `fsync`).
- With the software backend, keys, their states and pending destroy requests last only as long
  as the handle; its audit log file outlives them.

## Known differences

Differences between the two libraries that the contract leaves open and that no conformance test
pins:

| Area | C++ (`libekicore`) | Rust (`libekicore_rs`) |
|---|---|---|
| Audit path replaced by a FIFO while `eki_audit_verify` runs | opened with `O_NONBLOCK`, then refused as not a regular file | the path is examined, then opened; a swap in between makes the open wait for a writer |
| Flushing an audit record | `fcntl(F_FULLFSYNC)` on Apple platforms, with `fsync` as the fallback when a file system rejects it; `fsync` elsewhere | `sync_data`: `F_FULLFSYNC` on Apple platforms, with no fallback (a file system that rejects it makes the write fail with `EKI_ERR_BACKEND`); `fdatasync` on Linux |
| Exception or panic inside a logged operation | logged with status 10 after the changes registered so far are undone | logged with status 10, then the panic continues to the barrier; no undo |
| Loading the PKCS#11 module | `dlopen(RTLD_NOW \| RTLD_LOCAL)`, `C_GetFunctionList` only | `cryptoki` (`libloading`, lazy binding), `C_GetInterface` before `C_GetFunctionList` |
| Ending an object search | the result of `C_FindObjectsFinal` is checked | ignored |
| `C_WrapKey` | one call into a 40-byte buffer | a size query, then the call |
| PKCS#11 module path | any bytes | converted as bytes on Unix only |
| Invalid approver key at `eki_ks_destroy_approve` | `EKI_ERR_INVALID_ARGUMENT`, or `EKI_ERR_BACKEND` if OpenSSL cannot allocate | always `EKI_ERR_INVALID_ARGUMENT` |
| OpenSSL failures in verify paths | mapped to `EKI_ERR_AUTH_FAILED` or `EKI_ERR_INVALID_ARGUMENT` (fail closed) where RustCrypto cannot fail | n/a |
| AEAD AAD longer than 2^61 − 1 bytes | no check of its own; passed to OpenSSL in chunks | rejected (`EKI_ERR_INVALID_ARGUMENT` on seal, `EKI_ERR_AUTH_FAILED` on open); not reachable in practice |
| ECDSA nonces | random (OpenSSL, SoftHSM2) | RFC 6979 in the software store, random through PKCS#11 |
| Last-error text | its own wording | its own wording |

A caught Rust panic still prints its message through the panic hook to standard error. C++
`catch (...)` also catches the forced unwinding of thread cancellation, so cancelling a thread
inside a call into `libekicore` is not supported.
