# The ekicore C ABI contract

This document is the normative description of the C interface declared in
[`include/ekicore.h`](../include/ekicore.h). Both `libekicore` (C++, OpenSSL) and `libekicore_rs`
(Rust, RustCrypto) implement it, and the conformance harness checks that they behave identically.
Where this document and the header disagree on a declaration, the header wins; where they disagree
on behaviour, this document wins and the implementation is the bug.

## Purpose and scope

The ABI covers:

- HMAC-SHA256 (compute and constant-time verify),
- HKDF-SHA256 (RFC 5869, extract and expand in one call),
- AEAD: AES-256-GCM and ChaCha20-Poly1305 with detached 16-byte tags and 12-byte nonces,
- ECDSA P-256 / SHA-256 signature verification (`r || s` signatures, SEC1 uncompressed keys),
- a key store with a software backend and a PKCS#11 backend: generate, inspect, sign, HMAC, wrap
  and unwrap (RFC 3394 AES key wrap), destroy,
- a hybrid X25519 + ML-KEM-768 KEM, compiled in only with the `pq` feature / `EKI_WITH_PQ`.

Out of scope: certificates and PKI, key persistence for the software backend, streaming (all inputs
are complete buffers), and any algorithm not listed above.

The header is generated by cbindgen from the Rust declarations (`abi/` and `core-rs/src/ffi.rs`)
and committed. The C++ library compiles against the committed header, so the compiler enforces that
C++ matches it; CI regenerates the header with a pinned cbindgen and fails on any difference, which
enforces that Rust matches it ([`scripts/check-header.sh`](../scripts/check-header.sh)).

## Ownership and allocation

- The library never retains a caller pointer after a call returns. The strings in `eki_ks_config`
  are copied during `eki_ks_open`.
- The only object the library allocates for the caller is the opaque `eki_ks` handle. It is created
  by `eki_ks_open` and released only by `eki_ks_close` (which accepts NULL). The caller never frees
  it any other way.
- Every other output is written into caller-provided memory of the size documented per function.
- Strings returned by `eki_version` and `eki_status_name` have static storage and must not be freed.

## Pointer and length rules

For each input pair `(const uint8_t *p, size_t n)`:

| Case | Behaviour |
|---|---|
| `n == 0` | `p` may be NULL and is never dereferenced. |
| `n > 0` and `p == NULL` | `EKI_ERR_NULL_POINTER` |

The same rule applies to outputs whose size is given by an input length: `ct_out` (`pt_len`),
`pt_out` (`ct_len`), `okm` (`okm_len`).

Everything else must be non-NULL regardless of lengths: fixed-size inputs (`tag`, `public_key`,
`sig`, and the KEM's `pk`, `sk`, `ct`), fixed-size outputs, the `eki_ks *` handle, key id pointers,
`config`, `label`, and the `out` handle pointer of `eki_ks_open`.

Input and output buffers must not overlap. In-place AEAD is not supported.

## Labels

A label is a NUL-terminated byte string of 1 to 64 bytes (`EKI_LABEL_MAX_LEN`), every byte in
`0x20..=0x7E` (printable ASCII). The library reads at most 65 bytes; if no NUL appears within them
the call fails with `EKI_ERR_INVALID_ARGUMENT`. Labels need not be unique; keys are identified by
their 16-byte id.

## Validation order

Every function checks its inputs in the same order, and the first failing step decides the status:

1. NULL checks on every pointer parameter, in parameter order (`ks` first).
2. Selector validity (`alg`, `backend`): an unknown value gives `EKI_ERR_INVALID_ARGUMENT`; a known
   value whose support is not compiled in gives `EKI_ERR_UNSUPPORTED`. A function that is not
   compiled in at all (the hybrid KEM without `pq`) returns `EKI_ERR_UNSUPPORTED` at this step.
3. Length, range and format checks, in parameter order: `EKI_ERR_INVALID_ARGUMENT`. Fields of
   `eki_ks_config` are checked here in field order; a NULL field is `EKI_ERR_NULL_POINTER`.
4. Store state: `EKI_ERR_KEY_NOT_FOUND`, `EKI_ERR_WRONG_KEY_TYPE`, `EKI_ERR_KEY_EXISTS`, following
   the per-function order below.
5. Cryptographic verification: `EKI_ERR_AUTH_FAILED`.
6. Internal failure of OpenSSL or the PKCS#11 module: `EKI_ERR_BACKEND`.
7. A caught Rust panic or C++ exception: `EKI_ERR_INTERNAL`.

## Status codes

`eki_status` is a 32-bit enum. Values are stable and append-only: a value is never renumbered or
reused. Callers must be prepared for values they do not know; `eki_status_name` returns
`"EKI_STATUS_UNKNOWN"` for them.

| Value | Name | Meaning | Returned by |
|---|---|---|---|
| 0 | `EKI_OK` | Success; every output is fully written. | all status-returning functions |
| 1 | `EKI_ERR_NULL_POINTER` | A required pointer is NULL, or a non-empty buffer has a NULL pointer. | all status-returning functions |
| 2 | `EKI_ERR_INVALID_ARGUMENT` | Unknown selector, wrong length, value out of range, malformed label, unparseable public key, degenerate KEM input. | `eki_hmac_sha256`, `eki_hmac_sha256_verify`, `eki_hkdf_sha256`, `eki_aead_seal`, `eki_aead_open`, `eki_ecdsa_p256_verify`, `eki_ks_open`, `eki_ks_generate`, `eki_ks_unwrap`, `eki_hybrid_kem_encap`, `eki_hybrid_kem_decap` |
| 3 | `EKI_ERR_BUFFER_TOO_SMALL` | Reserved for future variable-length outputs; not returned in ABI version 1. | none yet |
| 4 | `EKI_ERR_UNSUPPORTED` | The selector is known but its support is not compiled in, or the whole function is not. | `eki_ks_open` (PKCS#11 off), hybrid KEM (`pq` off) |
| 5 | `EKI_ERR_AUTH_FAILED` | AEAD tag, HMAC tag, ECDSA signature or AES-KW integrity check failed. | `eki_hmac_sha256_verify`, `eki_aead_open`, `eki_ecdsa_p256_verify`, `eki_ks_unwrap` |
| 6 | `EKI_ERR_KEY_NOT_FOUND` | No object in the store carries the given key id. | `eki_ks_get_info`, `eki_ks_get_public_key`, `eki_ks_sign`, `eki_ks_hmac_sha256`, `eki_ks_wrap`, `eki_ks_unwrap` (the KEK), `eki_ks_destroy` |
| 7 | `EKI_ERR_KEY_EXISTS` | The key id requested for an unwrapped key is already in use. | `eki_ks_unwrap` |
| 8 | `EKI_ERR_WRONG_KEY_TYPE` | The key exists but its algorithm does not allow the operation. | `eki_ks_get_public_key`, `eki_ks_sign`, `eki_ks_hmac_sha256`, `eki_ks_wrap`, `eki_ks_unwrap` |
| 9 | `EKI_ERR_BACKEND` | OpenSSL or the PKCS#11 module failed internally; never caused by caller input. | all status-returning functions; stateless ones only when an algorithm cannot be fetched or memory cannot be allocated |
| 10 | `EKI_ERR_INTERNAL` | A panic or exception was caught at the boundary, or an internal invariant was violated. | all |

Input selectors (`eki_aead_alg`, `eki_key_alg`, `eki_ks_backend`) are plain `int32_t` typedefs with
`#define` values rather than C enums, so any value a C caller passes is representable on the Rust
side and an unknown one is rejected with a status instead of being undefined behaviour.

| Selector | Values |
|---|---|
| `eki_aead_alg` | `EKI_AEAD_AES_256_GCM = 1`, `EKI_AEAD_CHACHA20_POLY1305 = 2` |
| `eki_key_alg` | `EKI_KEY_AES_256 = 1` (32-byte secret, KEK, wrappable), `EKI_KEY_HMAC_SHA256 = 2` (32-byte secret, wrappable), `EKI_KEY_ECDSA_P256 = 3` (key pair, not wrappable) |
| `eki_ks_backend` | `EKI_KS_SOFTWARE = 1`, `EKI_KS_PKCS11 = 2` |

## Per-function contract

"Failures" lists the statuses beyond step 1 (NULL checks, which every function performs in
parameter order) in the order they are checked.

### Metadata

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_abi_version` | none | returns `EKI_ABI_VERSION` (1) | none |
| `eki_version` | none | static string `"ekicore-cpp <semver>"` or `"ekicore-rs <semver>"` | none |
| `eki_status_name` | `int32_t status` | static name such as `"EKI_ERR_AUTH_FAILED"`; never NULL | unknown value returns `"EKI_STATUS_UNKNOWN"` |

### Stateless primitives

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_hmac_sha256` | `key[key_len]`, `msg[msg_len]` | `out[32]` | `key_len == 0` → INVALID_ARGUMENT |
| `eki_hmac_sha256_verify` | `key[key_len]`, `msg[msg_len]`, `tag[tag_len]` | none | `key_len == 0` → INVALID_ARGUMENT; `tag_len != 32` → INVALID_ARGUMENT; constant-time mismatch → AUTH_FAILED |
| `eki_hkdf_sha256` | `ikm[ikm_len]`, `salt[salt_len]`, `info[info_len]` | `okm[okm_len]` | `ikm_len` 0 or > 32768; `salt_len` > 32768; `info_len` > 32768; `okm_len` 0 or > 8160 → INVALID_ARGUMENT, in that order. `salt_len == 0` means the RFC 5869 default salt. |
| `eki_aead_seal` | `alg`, `key[key_len]`, `nonce[nonce_len]`, `aad[aad_len]`, `pt[pt_len]` | `ct_out[pt_len]`, `tag_out[16]` | unknown `alg` → INVALID_ARGUMENT; `key_len != 32`; `nonce_len != 12`; `pt_len > EKI_AEAD_MAX_LEN` → INVALID_ARGUMENT. `aad_len` and `pt_len` may be 0. |
| `eki_aead_open` | `alg`, `key[key_len]`, `nonce[nonce_len]`, `aad[aad_len]`, `ct[ct_len]`, `tag[16]` | `pt_out[ct_len]` | as seal, with `ct_len`; then tag mismatch → AUTH_FAILED. `ct_len == 0` with a valid tag is OK. |
| `eki_ecdsa_p256_verify` | `public_key[65]`, `msg[msg_len]`, `sig[64]` | none | `public_key[0] != 0x04` → INVALID_ARGUMENT; key does not parse (off curve, coordinate ≥ p) → INVALID_ARGUMENT; `r` or `s` zero or ≥ n, or the signature does not verify → AUTH_FAILED. High-s signatures are accepted. |

Stateless functions return `EKI_ERR_BACKEND` only when an algorithm cannot be fetched or memory
cannot be allocated, never for a failure derived from the input.

### Key store

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_ks_open` | `config` | `*out` (NULL on failure) | unknown `backend` → INVALID_ARGUMENT; PKCS#11 not compiled in → UNSUPPORTED; PKCS#11 only: `pkcs11_module_path`, `pkcs11_token_label`, `pkcs11_user_pin` NULL (field order) → NULL_POINTER; token label not 1..=32 printable bytes, PIN not 1..=255 bytes → INVALID_ARGUMENT; module load, initialize, slot lookup or login failure → BACKEND. The software backend ignores the PKCS#11 fields. |
| `eki_ks_close` | `ks` (may be NULL) | none | none |
| `eki_ks_last_error_message` | `ks`, `buf[buf_len]` | message text, returns its full length | see [Last error message](#last-error-message) |
| `eki_ks_generate` | `ks`, `alg`, `label` | `id_out` (16 random bytes) | unknown `alg` → INVALID_ARGUMENT; label format → INVALID_ARGUMENT; backend failure → BACKEND |
| `eki_ks_get_info` | `ks`, `id` | `info_out` (`alg`, label NUL-padded through byte 64) | missing → KEY_NOT_FOUND (any key type is accepted) |
| `eki_ks_get_public_key` | `ks`, `id` | `out[65]` | missing → KEY_NOT_FOUND; not ECDSA_P256 → WRONG_KEY_TYPE |
| `eki_ks_sign` | `ks`, `id`, `msg[msg_len]` | `sig_out[64]` | missing → KEY_NOT_FOUND; not ECDSA_P256 → WRONG_KEY_TYPE |
| `eki_ks_hmac_sha256` | `ks`, `id`, `msg[msg_len]` | `out[32]` | missing → KEY_NOT_FOUND; not HMAC_SHA256 → WRONG_KEY_TYPE |
| `eki_ks_wrap` | `ks`, `kek_id`, `key_id` | `out[40]` | KEK missing → KEY_NOT_FOUND; key missing → KEY_NOT_FOUND; KEK not AES_256 → WRONG_KEY_TYPE; key not AES_256 or HMAC_SHA256 → WRONG_KEY_TYPE. Wrapping a key under itself is allowed. |
| `eki_ks_unwrap` | `ks`, `kek_id`, `blob[blob_len]`, `alg`, `label`, `id` | a new stored key with the given id | unknown `alg` → INVALID_ARGUMENT; `blob_len != 40` → INVALID_ARGUMENT; `alg == ECDSA_P256` → INVALID_ARGUMENT; label format → INVALID_ARGUMENT; KEK missing → KEY_NOT_FOUND; KEK not AES_256 → WRONG_KEY_TYPE; `id` already carried by any object → KEY_EXISTS; AES-KW integrity → AUTH_FAILED |
| `eki_ks_destroy` | `ks`, `id` | none | missing → KEY_NOT_FOUND (any key type; destroys every object with that id) |

The wrapped-key format is RFC 3394 AES key wrap of the 32-byte key value under a 256-bit KEK: 40
bytes, no header. It is the same as PKCS#11 `CKM_AES_KEY_WRAP`, OpenSSL `EVP_aes_256_wrap` and
RustCrypto `aes-kw`. The algorithm, label and id are not inside the blob; the caller supplies them to
`eki_ks_unwrap`.

### Hybrid KEM (optional)

| Function | Inputs | Outputs | Failures in order |
|---|---|---|---|
| `eki_hybrid_kem_keygen` | none | `pk_out[1216]`, `sk_out[96]` | not compiled in → UNSUPPORTED |
| `eki_hybrid_kem_encap` | `pk[1216]` | `ct_out[1120]`, `ss_out[32]` | not compiled in → UNSUPPORTED; all-zero X25519 shared secret → INVALID_ARGUMENT; ML-KEM encapsulation key fails the FIPS 203 modulus check → INVALID_ARGUMENT |
| `eki_hybrid_kem_decap` | `sk[96]`, `ct[1120]` | `ss_out[32]` | not compiled in → UNSUPPORTED; all-zero X25519 shared secret → INVALID_ARGUMENT. ML-KEM decapsulation never fails: implicit rejection yields a different secret. |

Layouts: `pk = x25519_pk(32) || mlkem768_ek(1184)`; `sk = x25519_sk(32) || mlkem768_seed d||z (64)`;
`ct = x25519_ephemeral_pk(32) || mlkem768_ct(1088)`. Decapsulation rebuilds `pk` from `sk`. The
combiner is

```
ss = HKDF-SHA256(ikm  = ss_x25519 || ss_mlkem,
                 salt = "",
                 info = "ekibridge-hybrid-x25519-mlkem768-v1" || ct || pk,
                 L    = 32)
```

## Outputs on error

On any status other than `EKI_OK`, every non-NULL output is zero-filled:

- fixed-size outputs over their full size;
- `info_out` over `sizeof(eki_key_info)`;
- a variable-length output over its declared length, but only if that length is within its valid
  range (`okm_len` in 1..=8160, `pt_len` / `ct_len` ≤ `EKI_AEAD_MAX_LEN`); otherwise it is left
  untouched.

On `EKI_OK` every output is fully written, and `eki_key_info.label` is NUL-padded through byte 64.
Struct padding bytes are unspecified; compare fields, never raw struct bytes.

`eki_aead_open` deserves a note: OpenSSL's GCM decryption writes plaintext before it checks the tag,
so the C++ library must zero `pt_out` on failure. RustCrypto leaves the buffer untouched on failure;
the Rust library zeroes it anyway, so the two are indistinguishable.

## Last error message

`size_t eki_ks_last_error_message(const eki_ks *ks, char *buf, size_t buf_len)` follows the
`snprintf` convention: it writes at most `buf_len - 1` bytes plus a NUL and returns the full length
of the message, excluding the NUL. `buf == NULL` is treated as `buf_len == 0`. With `ks == NULL` it
writes `""` if there is room and returns 0.

Every store call except `eki_ks_last_error_message` and `eki_ks_close` resets the message to `""` on
entry. A `EKI_ERR_BACKEND` failure always leaves a non-empty message containing the `CKR_*` name or
the OpenSSL error string; other failures may. Failures inside `eki_ks_open` have no handle and
report a status only. Message text is diagnostic and differs between the two libraries.

## Thread safety

- Stateless functions are thread-safe and reentrant.
- An `eki_ks` handle serialises all operations with an internal lock and may be shared between
  threads. The last-error message reflects the most recent operation on that handle by any thread.
- `eki_ks_close` must not race with any other call on the same handle.
- A poisoned Rust mutex (a panic while it was held) is recovered rather than propagated. C++
  `std::mutex` cannot be poisoned.
- PKCS#11 initialisation and login are per process. Two ekicore libraries loaded into one process
  must not hold PKCS#11 stores open at the same time; see the
  [threat model](threat-model.md#pkcs11-specifics).

## Secret handling

| | Rust (`libekicore_rs`) | C++ (`libekicore`) |
|---|---|---|
| Key material and intermediates | `zeroize`, `secrecy::SecretBox` | `SecretBuffer`: `OPENSSL_cleanse` on destruction, non-copyable, movable |
| Memory locking | not specified | `mlock` best effort, behind `EKI_MLOCK` |
| Destroyed or closed software keys | zeroised | zeroised |
| PKCS#11 PIN copy | zeroised after login | zeroised after login |
| Randomness | `getrandom::fill` | `RAND_bytes` |

With the PKCS#11 backend, secret and private keys are generated inside the token with
`CKA_SENSITIVE=TRUE`; their values never enter the library's memory. Secret keys are
`CKA_EXTRACTABLE=TRUE` only so that they can be wrapped; private EC keys are not extractable.

## Panic and exception barrier

Nothing but a status crosses the boundary. Every Rust `extern "C"` function runs its body inside
`catch_unwind`; every C++ `extern "C"` function wraps its body in `try { ... } catch (...)`. A caught
panic or exception becomes `EKI_ERR_INTERNAL`, with outputs zeroed as above. The Rust release profile
keeps `panic = "unwind"` so that panics can be caught at all.

## ABI stability and versioning

- `eki_abi_version()` returns `EKI_ABI_VERSION`, currently 1. It changes only for an incompatible
  change; additions that keep every existing declaration and behaviour do not change it.
- `eki_status` values are append-only.
- `eki_version()` returns `"<impl> <semver>"` where `<impl>` is `ekicore-cpp` or `ekicore-rs` and the
  semver equals the CMake project version and the Cargo package version.
- Optional features (`pkcs11`, `pq`) gate function bodies only, never declarations, so the header and
  the exported symbol set are the same in every build. A disabled function performs its NULL checks
  and returns `EKI_ERR_UNSUPPORTED`.
- Only `eki_*` symbols are exported ([`scripts/check-exports.sh`](../scripts/check-exports.sh)).

## Known limitations

- The wrapped-key blob does not authenticate its metadata (algorithm, label, id); see the
  [threat model](threat-model.md#known-limitations).
- The software key store lives only as long as its handle.
- The PKCS#11 PIN is passed as a NUL-terminated C string and lives in caller memory for the duration
  of `eki_ks_open`.
- `EKI_ERR_BUFFER_TOO_SMALL` is reserved and never returned in ABI version 1.
- Signatures produced by the two libraries are not byte-comparable: OpenSSL and SoftHSM2 use random
  nonces, RustCrypto `p256` uses RFC 6979 deterministic nonces. Signing is checked by
  cross-verification only.
